# First problem to look into 
After turning on the Moxie robot there is 5-to-7 wake-and-crash cycle which means Moxie's hardware is successfully triggering, but the internal software is immediately crashing or timing out when trying to talk to the AI cloud servers.Because original manufacturer Embodied Inc. shut down its official cloud servers, a Moxie trying to use standard, legacy firmware will ping an empty server, fail to authenticate, and crash right back into standby mode.

Probable Reasons Why It Is Happening 
- Server Handshake Timeout: Moxie registers the "wake up" command, starts the 7-second boot sequence (shows GRL logo on the screen), attempts to handshake with the backend servers, receives zero response, and automatically puts itself back to sleep to save power. 
- Network Band Dropping: Even if the robot is "connected" to your Wi-Fi router, if your router uses automatic band steering (combining 2.4GHz and 5GHz into one name), Moxie's antenna will frequently drop the connection mid-handshake, triggering an immediate shutdown
- Or it is because of cloud tts, which described in detail below

Check how it is resolved in openmoxie repository and implement the fix correctly in my repository.

Final goal: **the Moxie robot speaks audio synthesized by OpenAI** (Russian /

## 2. System architecture (what the pieces are)

### 2.1 Components

| Component | Role | Present in this repo? |
|---|---|---|
| **MQTT broker** (mosquitto, TLS :8883) | Transport between robot and server. Certs/config are OpenMoxie's, so the robot connects to it unchanged. | **[CONFIRMED] Yes** — `docker compose` builds the `mqtt` service from `mqtt.Dockerfile`. |
| **OpenMoxie "hive" Django backend** | Pairing, `config`/`schedule` push, the **remote-chat "brain"** (decides what Moxie says), STT, cloud-TTS answering. | **[CONFIRMED] No** — the `server` service is **commented out** in `docker-compose.yml`. Only the broker ships standalone. |

The critical gap: **standalone `docker compose` gives you a broker but no
brain.** Everything below follows from that.

### 2.2 MQTT topic contract  **[CONFIRMED unless noted]**

Device id used everywhere: `d_d05e3c66-dd29-4fe2-9758-7223e31511dc`.

| Topic | Direction | Payload | Used for |
|---|---|---|---|
| `/devices/{device}/state` | robot → server | JSON | Robot reports its state, including `settings.props.cloud_tts` and power state. This is the ground truth for what the robot actually applied. |
| `/devices/{device}/config` | server → robot | **plain JSON** (not protobuf) | Live settings push. `cloud_tts` lives at `settings.props.cloud_tts` = `"0"`/`"1"`. This is how you enable/disable cloud TTS without a reboot. |
| `/devices/{device}/commands/zmq` | server → robot | framed protobuf | `ProtoSubscribe` (declare which proto types to forward) **and** the outgoing `CloudTTSResponse` (the audio). |
| `/devices/{device}/events/zmq` | robot → server | framed protobuf | Robot-originated protos: `CloudTTSRequest`, `zmqSTTRequest` (forwarded mic audio). |
| `/devices/{device}/events/remote-chat` | robot → server | JSON | Robot's conversation requests to the brain (e.g. `{"query":"modules"}`, and per-turn conversational requests). **[TO VERIFY]** the exact response topic/shape the brain must reply on. |
| `/devices/{device}/schedule` | server → robot | JSON | Schedule push OpenMoxie performs after pairing. **[TO VERIFY]** whether the robot needs this to reach conversation mode. |

### 2.3 Wire framing for protobuf topics  **[CONFIRMED]**

Every protobuf message on the `.../zmq` topics is length-agnostic and prefixed
with its fully-qualified type name:

```
b"<fully.qualified.TypeName>:" + message.SerializeToString()
```

e.g. `b"embodied.unity.CloudTTSRequest:" + <bytes>`. Implemented in
`src/services/mqtt_service.py::_frame_proto` and matched on receipt in
`src/services/cloud_tts_request.py::parse_cloud_tts_request`.

### 2.4 The CloudTTS protobuf contract  **[CONFIRMED]**

From `src/protos/embodied/unity/CloudTTS.proto`:

```proto
enum RequestSourceType { ROBOT_TTS_REQUEST = 0; REMOTECHAT_TTS_REQUEST = 1; }

message CloudTTSRequest {                 // robot → server
  string markup   = 1;   // text to speak
  string event_id = 2;   // correlation id for THIS turn
  int32  chunk_num = 3;
  uint64 timestamp = 4;
  string user_id  = 5;
}

message CloudTTSResponse {                // server → robot (the audio)
  RequestSourceType request_source = 1;
  AudioBuffer audio = 2;                  // buffer + channels + sample_rate
  repeated TTSMark marks = 3;             // visemes/lip-sync (empty for now)
  string event_id = 4;                    // MUST echo the request's event_id
  int32  chunk_num = 5;                   // MUST echo the request's chunk_num
  ...
}
```

**The single most important rule:** the robot only plays a `CloudTTSResponse`
whose `event_id` (and `chunk_num`) match an outstanding request it is currently
waiting on. A response with any other `event_id` is silently discarded.
**[CONFIRMED]** — this is the root of the `/tts/speak` failure below.

## 3. The problem (root-cause analysis)

There are **three** distinct failures, in increasing order of severity. All
three trace back to *the absence of a remote-chat brain*.

### 3.1 The robot never enters conversation mode  **[CONFIRMED]**

With only the broker running, the robot repeatedly publishes remote-chat
queries — observed as `{"query":"modules"}` **14×** in one session on
`/devices/{device}/events/remote-chat` — and **nothing ever answers**. Because
no brain responds:

- The robot never learns its conversation modules/content.
- It never advances into an actual conversation turn.
- It therefore **never emits a `CloudTTSRequest`.** (Not once in any capture.)

This is the upstream cause. Everything the robot does in "cloud TTS" mode is
gated on it first having a brain to talk to.

### 3.2 `POST /tts/speak` cannot make the robot talk  **[CONFIRMED]**

`POST /tts/speak` → `speak_service.speak(text, language)` with **no
`event_id`**. In `src/services/speak_service.py`:

```python
if event_id is None:
    event_id = str(uuid.uuid4())   # a FRESH random id
```

The service then publishes a valid `CloudTTSResponse` carrying that random
`event_id`. The robot receives it (it *is* connected and framed correctly) but
**has no outstanding request with that id**, so per the rule in §2.4 it drops
the audio. Result: no sound, no error on the robot side.

`POST /tts/speak` is a useful **bench test of the OpenAI→WAV→MQTT publish
path**, but it is structurally incapable of driving playback, because real
playback requires an `event_id` the robot is actually waiting on — which only
exists inside a real conversation turn (§3.1).

### 3.3 Enabling `cloud_tts` standalone *breaks* the robot (the 5-second power-off)  **[CONFIRMED]**

During a live walkthrough we set `cloud_tts=1` to test. Observed:

```
17:46:22  we push cloud_tts = 1   (via /devices/{device}/config)
17:47:01  FIRST-EVER log: "Forcing IDLE state, MarkingUp has gone too long
                            without transitioning"
          ... robot force-idles → sleeps → screen off ~5s after waking
```

That "Forcing IDLE / MarkingUp" line **never appears before 17:46**. Mechanism:

- With `cloud_tts` **enabled**, the robot routes its speech through the cloud
  and enters the **"MarkingUp"** state, **waiting for a correlated
  `CloudTTSResponse`**.
- No brain issues a request and nothing answers with a matching `event_id`, so
  the wait times out. The robot **forces IDLE**, then sleeps → **screen off
  after ~5 seconds**.
- Worse: with `cloud_tts` on, the robot **suppresses its onboard TTS
  fallback**. So enabling it standalone makes the robot speak *less* than with
  it off (with it off, the robot at least uses local speech and stays awake).

**Fix that was applied during debugging:** revert `cloud_tts` to `0`. After the
revert took effect (`/state` reported `cloud_tts:"0"` at 17:58:48), the
MarkingUp stalls stopped completely and the robot stayed awake (STANDBY).

> **Operational note [CONFIRMED]:** the *enable* push applied instantly, but the
> *disable* push needed to be re-sent and took a few minutes to land — the robot
> appears to read `/devices/{device}/config` only at certain moments (fresh
> connect / while awake). **Always verify the change on `/devices/{device}/state`
> before relying on it. Never assume a config push applied.**

### 3.4 Conclusion of the analysis

```
No remote-chat brain
   └─ robot never enters a conversation turn
        └─ robot never emits a CloudTTSRequest (no event_id ever exists)
             ├─ /tts/speak's random event_id is always rejected      (§3.2)
             └─ enabling cloud_tts just makes the robot stall & sleep (§3.3)
```

**Therefore: the fix is not a one-line code change. You must reimplement the
part of OpenMoxie that answers the robot — the remote-chat brain — and only
then enable cloud TTS so your OpenAI audio is voiced on the turn's real
`event_id`.** This is "Option B" from prior notes; "Option A" (just flip
`cloud_tts` on and let the `CloudTTSRequest` handler answer) was **proven
insufficient** because the robot never gets far enough to emit a request.

## 4. The fix — reimplement OpenMoxie's remote-chat brain

### 4.1 What already exists in this repo (reuse it, do not rebuild it)

| Piece | File | Status |
|---|---|---|
| MQTT connect/TLS, framing, publish, inbound routing | `src/services/mqtt_service.py` | **Works.** Subscribes broadly, frames protos correctly, publishes `CloudTTSResponse` on `/commands/zmq`. |
| Inbound `CloudTTSRequest` → synthesis | `src/services/cloud_tts_request.py` | **Works.** Decodes the framed request and **echoes its `event_id`/`chunk_num`** back on the response — this is exactly right and is the piece that will finally light up once the robot actually emits requests. |
| OpenAI TTS | `src/services/synthesis/openai_tts.py`, `speak_service.py` | **Works.** text → WAV/PCM → `CloudTTSResponse`. |
| OpenAI STT | `src/services/stt/` | **Works.** audio → text. |
| OpenAI chat | `src/services/llm/` | **Works.** text → reply text (ru/kk, no translation). |
| Live `cloud_tts` toggle over MQTT | `tts_service.py` + `zmq_service.py` + `mqtt_service.publish_settings_update` | **Works.** Pushes `settings.props.cloud_tts` on `/config`. |

**The only missing component is the brain**: something that answers the robot on
`/devices/{device}/events/remote-chat` so it enters a conversation turn and
emits `CloudTTSRequest`s. Once that exists, `cloud_tts_request.py` +
`speak_service.py` already handle the audio correctly.

### 4.2 What to copy from OpenMoxie, and where it goes

You already run OpenMoxie in Docker, so **use your own OpenMoxie checkout as the
reference source.** In it, the relevant logic lives in the Django `hive`
application. Locate these responsibilities (filenames vary by OpenMoxie
version — **[TO VERIFY]** against your clone; do not guess):

1. **MQTT manager / dispatcher** — the module that subscribes to
   `/devices/+/#` and routes messages by topic. *You already have an equivalent*
   (`mqtt_service.py`); you only need to add a branch for the
   `.../events/remote-chat` topic. **Copy the routing logic, not the transport.**

2. **Remote-chat handler (the brain)** — the module that consumes a remote-chat
   request and produces a response. This is the piece to port. In OpenMoxie it
   typically:
   - answers the `{"query":"modules"}` / capability handshake so the robot knows
     what content is available and transitions into conversation; **[TO VERIFY]**
     the exact JSON schema of both the request variants and the responses, and
     the response topic (commonly a `/commands/remote-chat` or an inline reply on
     the same conversation channel).
   - for each conversational turn, generates reply text and drives TTS.

   **Port this handler into a new module**, e.g.
   `src/services/remote_chat.py`, mirroring the shape of the existing
   `cloud_tts_request.py` (a `handle_payload(payload: bytes|str)` entrypoint
   registered from the MQTT service).

3. **Device/pairing + config/schedule push** — enough of OpenMoxie's device
   bootstrap that the robot considers itself paired and provisioned. This repo
   already hardcodes the device config (`src/config.py::HARDCODED_DEVICE_CONFIG`)
   and can push it on `/config`. **[TO VERIFY]** whether the robot additionally
   requires a `/devices/{device}/schedule` push before it will enter
   conversation; if so, port OpenMoxie's schedule payload the same way.

4. **STT / cloud-TTS glue** — in OpenMoxie the brain hands recognized speech to
   the model and hands the reply to cloud TTS. **Do not copy OpenMoxie's AI
   providers** — wire the ported brain into this repo's existing OpenAI stages
   instead (`stt/`, `llm/`, `speak_service.speak(...)`).

> **How to port safely:** copy OpenMoxie's remote-chat handler as *reference for
> the message schema and state machine* (what the robot sends, what it expects
> back, in what order), and reimplement that contract in `src/services/`
> against this repo's MQTT/OpenAI plumbing. The value you are extracting from
> OpenMoxie is **the protocol**, not its Python.

### 4.3 The end-to-end turn flow you are building

```
Robot                         This service (brain + OpenAI)              Robot
  │  remote-chat handshake  ─────────────►  answer modules/capabilities
  │                          ◄───────────── (robot now enters conversation)
  │  mic audio (zmqSTTRequest, /events/zmq) ─► OpenAI STT ─► user text
  │                                            OpenAI chat ─► reply text (ru/kk)
  │  CloudTTSRequest(event_id=E, markup=…)  ─►  [option 1: robot asks us to speak]
  │      on /events/zmq                          cloud_tts_request.handle_payload
  │                                              → speak_service.speak(
  │                                                    text, lang,
  │                                                    event_id=E,   ← echo!
  │                                                    chunk_num=…)
  │                                              → OpenAI TTS → CloudTTSResponse
  │  CloudTTSResponse(event_id=E, audio)    ◄──  published on /commands/zmq
  │  ▶ PLAYS AUDIO (event_id matches)                                    ✅
```

If your ported brain drives TTS itself (rather than waiting for the robot to
emit a `CloudTTSRequest`), it must still publish a `CloudTTSResponse` whose
`event_id` matches the turn the robot is currently marking up, with
`request_source = REMOTECHAT_TTS_REQUEST`. **[TO VERIFY]** which of the two
patterns your robot firmware uses (robot-pull `CloudTTSRequest` vs.
brain-push on the turn id) — confirm from a live capture with OpenMoxie running,
then mirror exactly that pattern. This repo's `speak_service.speak(...)` already
accepts `event_id`, `chunk_num`, and `request_source`, so either pattern is a
parameter choice, not new code.

## 5. How `cloud_tts` must be enabled (exactly)

`cloud_tts` is a live setting at `settings.props.cloud_tts` (`"0"`/`"1"`),
pushed as **plain JSON** on `/devices/{device}/config`. This repo does it via:

- **HTTP:** `POST /tts/cloud-tts  {"enabled": true}` (Swagger at `/docs`)
- which flows `tts_service.request_toggle` → ZMQ bus → `tts_service._apply_toggle`
  → `mqtt_service.publish_settings_update(device, config)` (when
  `OPENMOXIE_ENABLED=false`, the standalone path).

**The ordering rule is mandatory (see §3.3):**

1. **First** stand up the remote-chat brain (§4) and confirm the robot enters a
   conversation turn (it emits remote-chat traffic that you answer, and — if the
   pull pattern — a `CloudTTSRequest`).
2. **Only then** enable cloud TTS: `POST /tts/cloud-tts {"enabled": true}`.
3. **Verify** on `/devices/{device}/state` that `settings.props.cloud_tts` has
   actually flipped to `"1"` before trusting it. If it hasn't within ~30–60s,
   re-push (the robot reads `/config` only at certain moments).
4. If anything goes wrong, **disable immediately**
   (`POST /tts/cloud-tts {"enabled": false}`) and re-verify on `/state`.
   Leaving it enabled with nothing answering will stall and sleep the robot.

**Never enable `cloud_tts` before the brain is answering.** That is precisely
what produced the 5-second power-off.

## 6. Running everything

### 6.1 Prerequisites

- `mise`, `uv`, Docker Desktop, Python 3.12 (pinned in `mise.toml`).
- `OPENAI_API_KEY` in the environment (see §8 — do **not** rely on the value
  currently committed in `src/config.py`).
- The robot on the same LAN, configured to reach this machine's broker.

### 6.2 Start the MQTT broker (this repo, standalone)

```bash
docker compose up mqtt      # mosquitto on :8883, OpenMoxie certs/config
```

This is the only container needed for the broker. (The `server` service is
intentionally commented out — this repo replaces it.)

### 6.3 Start this service

```bash
mise dev
# equivalently: uv run fastapi dev src/main.py --reload-dir src
```

> **Note [CONFIRMED]:** `mise dev` must run through `uv` so it uses the project
> venv (Python 3.12), not system Python 3.13. This is already fixed in
> `mise.toml` (`dev = "uv run fastapi dev src/main.py --reload-dir src"`). A bare
> `fastapi …` command resolves to system Python and fails.

Swagger UI: `http://localhost:8000/docs`. A `ConnectionRefused` to MQTT at
startup just means the broker isn't up yet — start §6.2 first.

### 6.4 Power on the robot

1. Power on Moxie; it connects to the broker over TLS :8883.
2. Confirm the connection: watch this service's logs and/or
   `/devices/{device}/state` messages appear for
   `d_d05e3c66-dd29-4fe2-9758-7223e31511dc`.
3. With the **brain running** (§4), confirm the robot answers the remote-chat
   handshake and enters conversation.
4. Enable cloud TTS **only now**, following §5, and verify on `/state`.
5. Speak to the robot (or trigger a turn). The turn's `CloudTTSRequest` /
   response cycle carries a real `event_id`, so the OpenAI audio plays. ✅

### 6.5 Bench-testing OpenAI stages without the robot

These do not require the robot and are safe any time:

- `POST /tts/transcribe` — upload WAV → OpenAI STT → text.
- `POST /tts/respond` — text → OpenAI chat → reply text.
- `POST /tts/speak` — text → OpenAI TTS → publishes a `CloudTTSResponse`.
  **This confirms the synthesis+publish path only; it will NOT make the robot
  talk** (random `event_id`, §3.2). Do not use it as a proof of end-to-end
  success.

## 7. How to verify the fix worked

The fix is correct when **all** of these hold:

1. The robot's `/devices/{device}/events/remote-chat` handshake is answered and
   the robot transitions into conversation (no endless `{"query":"modules"}`
   repeats).
2. A conversation turn produces either a `CloudTTSRequest` on `/events/zmq`
   (pull pattern) or a brain-issued turn id (push pattern) — with a concrete
   `event_id`.
3. This service publishes a `CloudTTSResponse` on `/commands/zmq` whose
   `event_id` **matches** that turn.
4. **Moxie plays the OpenAI audio**, and there are **no** "Forcing IDLE state,
   MarkingUp has gone too long without transitioning" lines in the robot log.
5. The robot stays awake (screen on / STANDBY, not force-sleeping).
